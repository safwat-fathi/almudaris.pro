# 1. 🧭 Overview

This document defines the **functional and non-functional system requirements** for Al-Mudaris Pro MVP.

The system is built on a **unified User model** where all actors (Teacher, Parent, Student) are users, with role-based behavior and permissions.

Core pillars:

* Unified User entity
* Parent–Student ownership relationship
* Student lifecycle (Pending → Active)
* Teacher-controlled group assignment

---

# 2. 🧱 System Actors (Role-Based Users)

All actors are represented as **Users with roles**.

## Roles:

* Teacher
* Parent
* Student

---

## 2.1 Teacher

* Creates groups
* Adds students (Quick Add / Invite)
* Assigns students to groups
* Manages attendance, payments, homework

## 2.2 Parent

* Owns student accounts
* Creates and manages student users
* Links students to teachers
* Views academic data

## 2.3 Student

* Has a user account created by parent
* Logs in using phone + password
* Can view personal academic data

---

# 3. 🧠 Core Domain Model

## 3.1 Entities

### User (Unified Entity - CRITICAL)

* id
* name
* phone
* password
* role (teacher | parent | student)
* is_active (boolean)

---

### ParentStudent (CRITICAL RELATION)

Defines ownership relationship

* parent_id (User)
* student_id (User)

Rules:

* Parent can have multiple students
* Each student must belong to exactly one parent

---

### ParentTeacher

Defines parent-teacher relationship

* parent_id (User)
* teacher_id (User)

Rules:

* Parent can have multiple teachers
* Teacher can have multiple parents

---

### TeacherStudent

Defines teaching relationship

* teacher_id (User)
* student_id (User)
* status (pending | active)

---

### Group

* id
* teacher_id
* name
* price
* status (open | full | closed)

---

### GroupEnrollment

* id
* group_id
* student_id
* status (pending | active)

---

# 4. 🔁 Student Lifecycle

## 4.1 Pending Student Creation (Teacher Quick Add)

### Input:

* student_name (required)
* parent_phone (required)
* student_phone (optional)

### Behavior:

* System creates User with role = student (inactive)
* Creates Student Profile with status = pending
* Creates TeacherStudent relationship (pending)
* Add student to Parent account as pending if Parent confirmed create ParentStudent relationship

---

## 4.2 Parent Claim Flow

### Trigger:

* Parent opens invitation

### System Behavior:

#### Case 1: Parent exists

* Authenticate parent and link Teacher to parent

#### Case 2: Parent does not exist

* Register parent and link Teacher to parent

---

### Student Resolution:

Parent must choose:

* Link to existing student
* Create new student (new User with role = student)
* Merge duplicate

---

### Output:

* Student status → active
* User.is_active → true (for student if login enabled)
* ParentStudent relationship created
* TeacherStudent status → active

---

# 5. 📩 Invitation System

## 5.1 Invitation Types

### Parent Invitation (Primary)

* Generated by teacher
* Delivered via link / QR

### Auto Invitation

* Triggered after Quick Add

---

## 5.2 Invitation Capabilities

System must support:

* Parent authentication
* Student resolution (create / link / merge)
* Creation of ParentStudent relationship
* Teacher-student linking

---

# 6. 👨‍🏫 Teacher Functional Requirements

## 6.1 Quick Add Student

* Creates student as User (role = student)
* Student is marked as pending
* Parent phone is mandatory
* Invitation must be sent

---

## 6.2 Assign Student to Group

### Preconditions:

* TeacherStudent relationship exists

### Behavior:

* Teacher selects student
* Teacher selects group

### Constraints:

* Only teacher can assign
* Group must be open

---

## 6.3 Unassigned Students View

System must provide:

* Students linked to teacher but not in any group
* Show status (pending / active)

---

# 7. 👨‍👩‍👦 Parent Functional Requirements

## 7.1 Student Management

* Create student account (User with role = student)
* View owned students
* Link students to teachers via invite

---

## 7.2 Restrictions

* Cannot assign groups
* Cannot create teacher relationships directly

---

# 8. 👨‍🎓 Student Functional Requirements

## 8.1 Authentication

* Login via phone + password
* Account must be created by parent

---

## 8.2 Permissions

* View own attendance
* View own homework
* View own payment status

---

## 8.3 Restrictions

* Cannot edit profile
* Cannot manage relationships

---

# 9. 👥 Group Management

## 9.1 Group States

* open → accepts students
* full → cannot accept new students
* closed → inactive

---

## 9.2 Enrollment Rules

* Only teacher assigns
* Student can be:

  * pending in group
  * active in group

---

# 10. 📊 Attendance

* Mark per student per group
* Supports pending and active students

---

# 11. 💰 Payments

* Monthly tracking per student
* Optional restriction: only active students fully tracked

---

# 12. 📚 Homework

## Teacher

* Create / edit / delete

## Parent / Student

* View per student

---

# 13. 🔐 Access Control Rules

* Parent owns student identity
* Student accounts must be created via parent
* Teacher cannot finalize student ownership
* Student cannot self-register

---

# 14. ⚠️ Data Integrity Rules

* No duplicate student users
* ParentStudent relationship is mandatory for active students
* Merge flow required

---

# 15. 🚀 Non-Functional Requirements

## Performance

* Attendance marking < 3 seconds

## Usability

* Mobile-first
* Minimal steps for teacher actions

## Reliability

* Invitation must be retryable

---

# 16. 📌 Key Constraints

* No parent group selection
* No automatic group assignment
* No student self-registration

---

# 17. 🔮 Future Considerations

* Advanced student permissions
* Smart matching
* Auto group suggestions
* Multi-teacher dashboards

---

# ✅ Summary

This SRS enforces:

* Unified User model (Teacher, Parent, Student)
* Explicit Parent–Student ownership relationship
* Teacher-controlled group assignment
* Clean separation between linking and enrollment
* Pending → Active lifecycle as core system behavior
